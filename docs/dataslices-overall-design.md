# DataSlices / 数据切片：总体设计

> 文档状态：基线设计 v1.0  
> 更新时间：2026-07-27  
> 作用：定义 DataSlices 的定位、内容结构、视觉系统、目录规范与发布方式。各故事的具体设计必须在此基础上单独版本化。

## 1. 项目定位

DataSlices 是一个中文数据叙事网站，目标不是堆放图表，而是像切开一个熟悉对象那样，用数据、可视化和长篇叙事揭示日常经验背后的另一层结构。

核心表达：

> 切开熟悉世界，看见数据里面的另一层。

参照对象是 The Pudding 一类滚动数据故事，但不复制其视觉形式。DataSlices 应形成自己的特点：

- 中文长篇叙事；
- 强调真实数据和方法透明度；
- 每篇至少有一个能被读者记住的主视觉隐喻；
- 互动必须承担解释、比较或代入任务，而不是装饰；
- 每个故事同时保存正文、设计、数据、方法和网站源码。

## 2. 内容目标

### 2.1 单篇故事

正式故事应满足：

- 一个清晰的核心问题；
- 由现象、尺度、机制、差异、影响和行动组成的完整证据链；
- 真实活跃阅读时间原则上达到 8—10 分钟；
- 正文约 2,800—3,400 个汉字，具体以内容需要为准；
- 1 个 Hero 主视觉；
- 2—3 个大型互动；
- 4—6 个辅助视觉；
- 方法、数据年份、模型与限制可查询。

页面不得仅凭长度标注阅读时间。正式上线后至少邀请五名首次阅读者测试，以活跃阅读时间中位数为准。

### 2.2 网站层级

网站首页负责：

- 解释 DataSlices 品牌；
- 展示全部故事卡片；
- 提供统一导航；
- 标注故事主题、状态和阅读时间；
- 未来支持“城市”“科技”“环境”“社会”等主题筛选。

每个故事使用稳定路径：

```text
/stories/<story-slug>/
```

## 3. 仓库作为唯一真源

GitHub 仓库是唯一可追溯主版本。发布网站必须来自仓库中的同一套文件。

```text
dataslices/
├── index.html
├── styles.css
├── docs/
│   ├── dataslices-overall-design.md
│   ├── editorial-principles.md
│   └── story-template.md
├── stories/
│   └── <story-slug>/
│       ├── index.html
│       ├── story.css
│       ├── story.js
│       ├── docs/
│       │   ├── 01-concept-design-v1.md
│       │   ├── 02-storyboard-wireframes-v2.md
│       │   ├── manuscript.md
│       │   ├── methodology.md
│       │   ├── sources.md
│       │   └── implementation-traceability.md
│       ├── data/
│       └── assets/
└── .github/workflows/pages.yml
```

新的网页代码不得先于故事设计文档出现。设计发生变化时，先更新设计文档和决策记录，再修改实现。

## 4. 制作流程

1. **选题设计**：明确核心问题、独特视角和潜在视觉隐喻。
2. **数据可行性核验**：确认数据是否存在、年份是否兼容、是否允许公开再分发。
3. **总体故事设计**：完成章节、情绪曲线、主要互动和阅读时长分配。
4. **v1 概念设计稿**：确定核心叙事模块和主视觉方向。
5. **v2 逐章线框稿**：明确每屏文案、布局、交互状态和滚动节奏。
6. **方法文档**：标明哪些是观测、模型、估算和情景。
7. **网页实现**：严格建立设计—实现映射。
8. **验证**：数据、浏览器、手机端、无障碍、性能和阅读时间测试。
9. **发布**：通过 GitHub Pages 部署，并记录 commit。

## 5. 视觉系统

### 5.1 总体气质

- 高级编辑设计，而不是企业仪表盘；
- 大留白与强节奏；
- 允许不同故事拥有独立主题色；
- 避免“所有图表都放在卡片中”的模板感；
- 页面变化应来自故事语义，而非单纯视觉炫技。

### 5.2 字体与排版

- 标题可使用宋体或编辑感衬线字体；
- 正文使用高可读无衬线字体；
- 移动端正文原则上不小于 17px；
- 单行约 22—30 个汉字；
- 每段通常 3—5 行；
- 金句只用于叙事转折，不能滥用。

### 5.3 动效原则

- 动效必须对应真实机制；
- 滚动驱动状态改变时，应提供清楚的开始、过程与结果；
- 避免无意义粒子、弹跳、爆炸和过度视差；
- 尊重 `prefers-reduced-motion`；
- 手机端不得依赖 hover。

## 6. 数据与事实规范

- 不把卫星夜光直接等同于人眼天空亮度；
- 不把不同年代、不同传感器的数据无缝拼接成单一精确曲线；
- 模型输出必须写“估算”“区间”或“情景”；
- 演示数据不得在正式页面中伪装成实测数据；
- 所有来源保存原始链接、年份、访问日期和许可证；
- 对重要数字给出方法入口和限制说明。

## 7. 技术方案

首阶段采用静态 HTML、CSS、JavaScript：

- 无需后端即可由 GitHub Pages 发布；
- 数据预处理为本地 JSON；
- 第三方服务失效时故事仍能阅读；
- 图形优先使用 Canvas、SVG 和原生 DOM；
- 需要地图时使用可静态部署的 GeoJSON 与前端渲染；
- 不在页面运行时请求昂贵或受限接口。

后续可以引入构建工具，但必须保持可归档和可复现。

## 8. 发布架构

- 主仓库：`tseng71/dataslices`
- 正式发布：GitHub Pages
- 默认目标地址：`https://tseng71.github.io/dataslices/`
- 发布源：`main` 分支 + GitHub Actions
- 每次正式版本应打 tag，例如 `story-disappearing-stars-v1.0`

ChatGPT Sites 不再作为发布目标。

## 9. 完成定义

一个故事只有在以下条件全部满足时才可标记为“完成”：

- 设计文档、正文、方法、来源和数据文件齐全；
- 所有核心图形接入正式数据，或清楚标为示意；
- 桌面端与移动端经过实际浏览器测试；
- 无严重控制台错误、断链或不可操作互动；
- 关键事实和数字经过复核；
- 阅读时间经过测试；
- GitHub Pages 已成功公开访问；
- README 和版本记录已更新。
